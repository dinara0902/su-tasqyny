## 1. A\* және BFS: қауіпсіз жолды табу

### Бір сөйлеммен

A\* — үйден пунктке дейінгі ең арзан жолды табатын алгоритм. Ол картаны түгел қарамайды, мақсатқа жақын бағыттағы жолдарды бірінші тексереді.

### Өмірдегі мысал

Сен бейтаныс ауылда дүкен іздеп жүрсің. Әр қиылыста екі нәрсені ойлайсың:
- **осы жерге дейін қанша жүрдім** (бұл — `g`);
- **дүкенге дейін шамамен тағы қанша қалды** (бұл — `h`).

Екеуін қосып, `f = g + h` ең кіші болатын бағытпен жүресің. A\* дәл осылай ойлайды.

### BFS-тен айырмасы

**BFS** мақсат қай жақта екенін білмейді. Ол бастапқы нүктеден барлық жаққа бірдей таралады, су толқыны сияқты: алдымен 1 қадамдағы ұяшықтар, сосын 2 қадамдағылар, т.с.с. Ақыры мақсатқа жетеді, бірақ көп артық ұяшық қарайды.

**A\*** мақсаттың бағытын `h` арқылы біледі, сондықтан артық ұяшықтарды аз қарайды.

**Біздің картадағы мысал.** Сейітовтер отбасының үйінен (1, 1) Мәдениет үйіне (1, 11) дейін:

| | Жол ұзындығы | Зерттелген ұяшықтар |
|---|---|---|
| BFS | 14 қадам | 39 |
| A\* | 14 қадам | 17 |

Жол бірдей, бірақ A\* екі еседен көп аз ұяшық қарады. *(Сандар біздің тексеру есебінен алынды; сенің кодыңда тең жағдайларды қалай таңдайтыныңа байланысты сәл өзгеше болуы мүмкін.)*

### `h` қалай есептеледі

Біз тек 4 бағытта жүреміз, сондықтан **Манхэттен қашықтығы** қолданамыз:

```
h = |x − x_мақсат| + |y − y_мақсат|
```

Мысалы, (1, 1) мен (1, 11) арасы: |1 − 1| + |1 − 11| = **10**. Яғни қабырғалар болмаса, кемінде 10 қадам керек. Шын жол 14, себебі қабырғаларды айналып өтеміз.

**Маңызды:** `h` шын қашықтықтан **ешқашан үлкен болмауы керек**. Бұл қасиет **admissible** (асыра бағаламайтын эвристика) деп аталады. Сонда ғана A\* ең арзан жолды табатынына кепілдік бар. Манхэттен қашықтығы қабырғаларды ескермейді, сондықтан шын жолдан әрқашан кіші немесе тең.

### Су қаупі жолға қалай әсер етеді

Әр қадамның «бағасы» бар:

```
баға = 1 + 10 · P(су басты)
```

- Құрғақ жол: P = 0, баға = **1**.
- Көпір (P = 0.6): баға = 1 + 6 = **7**. Яғни A\* көпірден басқа жол болса, сонымен жүреді.
- P > 0.7 болса, жол **жабық**: A\* ол арқылы мүлдем өтпейді.

P мәнін Динараның Байес модулі береді.

### Код қалай жұмыс істейді (қадамдар)

1. `open` тізімі: «әлі тексерілмеген, бірақ барып көруге болатын» ұяшықтар. Басында онда тек бастапқы үй.
2. `open`-нан `f` ең кіші ұяшықты аламыз.
3. Ол пункт болса — жол табылды, тоқтаймыз.
4. Әйтпесе әр көршіге: «осы көршіге осы жақтан келсем, `g` бұрынғыдан аз бола ма?» Аз болса, `g`-ні жаңартамыз, «қайдан келдім» деп жазып қоямыз (`cameFrom`) және көршіні `open`-ға қосамыз.
5. 2-қадамға қайтамыз.
6. Жолды қалпына келтіру: пункттен бастап `cameFrom` бойынша артқа жүріп, үйге жетеміз.

Функциялардың нақты кірісі мен шығысы: [`SPEC.md`, 4-бөлім](SPEC.md#4-a-және-bfs-2-апта).

### BFS коды жол-жолымен

Код: `src/algorithms/search.js` → `bfs`. Негізі — дәрістегі «BFS: complete code» (Python). Алгоритм сол күйі, тек біздің картаға бейімделді.

| Дәріс (Python) | Біздің код (JavaScript) | Не өзгерді |
|---|---|---|
| `queue = deque([(start, [start])])` | `queue = [{ cell: start, path: [start] }]` | бірдей: кезекте ұяшық және оған дейінгі жол |
| `while queue:` | `while (queue.length > 0)` | бірдей |
| `state, path = queue.popleft()` | `const { cell, path } = queue.shift()` | бірдей: кезектің **басынан** аламыз |
| `print("Exploring:", state)` | `order.push(cell)` | басып шығармаймыз, тізімге жазамыз: сайт «толқынды» осы тізім бойынша көрсетеді |
| `if state == goal: return path` | `if (goalKeys.has(...)) return { found: true, path, ... }` | **1.** бізде 3 пункт, кез келгені жарайды; **2.** SPEC талап еткен толық нәтижені қайтарамыз |
| `for next_state in graph[state]:` | `for (const next of MapUtil.neighbors(...))` | **3.** көршілерді `map.js`-тегі `neighbors` береді |
| — | `if (visited.has(k)) continue` | **4.** visited жоқ болса, BFS шеңбер бойымен жүреді: A → B → A → B… (дәрістегі «The Role of the Visited Set») |
| — | `if (isClosed(...)) continue` | **5.** су басқан ұяшық (P > 0.7) арқылы өтпейміз |
| `path + [next_state]` | `[...path, next]` | бірдей: ескі жолды өзгертпей, жаңа тізім жасаймыз |
| `return None` | `return { found: false, cost: Infinity, ... }` | жол жоқ |

Басындағы екі жол:
- `MapUtil.cellAt(map, start.x, start.y)` — бастапқы нүкте картадан тыс болса, түсінікті қате шығады.
- `goalKeys` — пункттерді `"22,1"` сияқты жолдарға айналдырамыз. JavaScript-те `{x: 22, y: 1}` екі объектіні `==` арқылы салыстыруға болмайды, ал жолдарды салыстыруға болады.

**Қайтаратын нәтиже:**
- `found` — жол табылды ма;
- `path` — жол: `[{x, y}, ...]`, үйден пунктке дейін;
- `cost` — қадам саны (`path.length - 1`, себебі бастапқы ұяшық қадам емес);
- `goal` — қай пунктке жеттік;
- `expanded` — неше ұяшық зерттелді (A\*-пен салыстыру үшін);
- `order` — зерттеу реті («Қалай ойлады?» режимі үшін).

**Неге visited-ке кезекке салған сәтте қосамыз, алған сәтте емес?** Бір ұяшыққа бірнеше көршіден жетуге болады. Кезектен алғанда ғана белгілесек, ол ұяшық кезекке бірнеше рет түсіп, артық жұмыс істейміз. Кезекке салған сәтте белгілесек, әр ұяшық кезекке тек бір рет түседі. Нәтиже өзгермейді, бірақ жылдамырақ.

**Біздің картадағы нәтиже:**
- Сейітовтар үйі (1, 1) → Мәдениет үйі (S2): 14 қадам, 39 ұяшық зерттелді.
- Батыс жақтағы үй (1, 7) → №1 мектеп (S1), көпір арқылы: 35 қадам.
- Көпірді су басса (P = 0.9): сол маршрут жоғалады, `found: false`. Батыс жақтан шығыс жаққа өтудің жалғыз жолы — көпір.

### A\* коды жол-жолымен

Код: `src/algorithms/search.js` → `heuristic`, `stepCost`, `buildPath`, `aStar`. Негізі — дәрістегі «A\* Search – Grid Pathfinding Example» (Python). Дәрістегі мысал да тор (grid) бойынша жұмыс істейді, сондықтан өзгеріс аз.

| Дәріс (Python) | Біздің код (JavaScript) | Не өзгерді |
|---|---|---|
| `manhattan(a, b)` | `heuristic(cell, goals)` | **1.** бізде 3 пункт: ең жақынына дейінгі Манхэттен қашықтығын аламыз |
| `get_neighbors(pos, grid)` | `MapUtil.neighbors(map, x, y)` | бірдей идея, `map.js`-те жазылған |
| `heapq.heappush(frontier, (h, 0, start))` | `frontier = [{ f, g: 0, cell: start }]` | **2.** JavaScript-те `heapq` жоқ: қарапайым тізім |
| `heapq.heappop(frontier)` | `for` арқылы f ең кішісін іздеп, `splice` арқылы аламыз | мағынасы бірдей: f ең кіші ұяшық |
| `came_from = {start: None}` | `cameFrom = new Map([[startKey, null]])` | бірдей |
| `cost_so_far = {start: 0}` | `costSoFar = new Map([[startKey, 0]])` | бірдей |
| — | `if (g > costSoFar.get(currentKey)) continue` | **3.** ескірген жазбаны өткізіп жібереміз: ұяшыққа кейін арзанырақ жол табылса, ескі жазба кезекте қалып қояды |
| `if current == goal: break` | `if (goalKeys.has(currentKey)) return {...}` | **4.** 3 пункттің кез келгені; бірден толық нәтиже қайтарамыз |
| `new_cost = g + 1` | `newCost = g + stepCost(...)` | **5.** қадам құны = 1 + 10 · P(F). Су қаупі бар ұяшық «қымбат» |
| — | `if (isClosed(...)) continue` | **6.** P > 0.7 болса, ұяшық жабық |
| `if neighbor not in cost_so_far or new_cost < cost_so_far[neighbor]` | дәл солай | бірдей |
| `f = new_cost + manhattan(neighbor, goal)` | `f: newCost + heuristic(next, goals)` | бірдей: **f = g + h** |
| `came_from[neighbor] = current` | `cameFrom.set(nextKey, current)` | бірдей |
| `return came_from, cost_so_far[goal]` | `buildPath(cameFrom, current)` | **7.** жолды өзіміз қалпына келтіреміз: мақсаттан `cameFrom` бойынша артқа жүріп, сосын тізімді аударамыз |

**Неге Манхэттен эвристикасы дұрыс (admissible)?** Бір қадамның құны кемінде 1 (су қаупі тек қосады). Ал Манхэттен қашықтығы — қабырғасыз картадағы ең аз қадам саны. Сондықтан h нақты қалған құннан ешқашан аспайды, ал мұндай эвристикамен A\* ең арзан жолды табады.

**Біздің картадағы нәтиже (су жоқ, 11 үйдің бәрі):**
- A\* пен BFS жолының ұзындығы 11 үйдің бәрінде **бірдей**.
- A\* барлығы **180** ұяшық зерттеді, BFS **410**. Яғни A\* шамамен 2,3 есе аз жұмыс істейді.
- Мысал: Сейітовтар үйі (1, 1): A\* 17 ұяшық, BFS 39.

**Су қаупі қалай әсер етеді:** батыс жақтағы үй (1, 7) → №1 мектеп. Көпірдің екі ұяшығына P = 0.5 берсек, жол сол күйі көпір арқылы өтеді (басқа жол жоқ), бірақ құны 35-тен 45-ке өседі: әр қауіпті ұяшық 1 емес, 1 + 10 · 0.5 = 6 тұрады. P = 0.9 болса, көпір жабылады, `found: false`.

### Қорғаудағы сұрақтар

**f, g, h деген не?**
g — бастаудан осы ұяшыққа дейінгі нақты баға, h — осы ұяшықтан мақсатқа дейінгі болжам, f = g + h — осы ұяшық арқылы өтетін жолдың болжамды толық бағасы.

**Неге Манхэттен қашықтығы?**
Біз диагональмен емес, тек 4 бағытта жүреміз. Манхэттен қашықтығы шын жолдан ешқашан үлкен емес, сондықтан A\* ең арзан жолды табады.

**Неге A\* BFS-тен жақсы?**
Жол бірдей, бірақ A\* аз ұяшық қарайды, себебі мақсаттың бағытын біледі. Біздің мысалда 17 мен 39.

**Жол табылмаса не болады?**
Мысалы, көпір жабылып, үй пункттен бөлек қалса, функция `found: false` қайтарады, ал сайт «қауіпсіз жол жоқ» деп жазады. Бағдарлама қатып қалмайды.

## 2. CSP: адамдарды пункттерге бөлу

### Бір сөйлеммен

CSP (шектеулерді қанағаттандыру есебі) — барлық ережені бұзбай, әр отбасына бір пункт таңдау.

### Өмірдегі мысал

Мектепте сынып жетекшісі оқушыларды автобусқа отырғызып жатыр. Ережелер: автобусқа 40-тан артық адам сыймайды, дос-құрбылар бірге отырады, ауырып жүрген бала дәрігері бар автобусқа отырады. Сынып жетекшісі бір-бірлеп отырғызады, тұйыққа тірелсе, біреуін басқа автобусқа ауыстырады. CSP дәл осылай жұмыс істейді.

### Үш ұғым

| Ұғым | Мағынасы | Біздің есепте |
|---|---|---|
| **Айнымалы** | не таңдаймыз | әр отбасы (F1, F2, …) |
| **Домен** | ненің ішінен таңдаймыз | отбасы бара алатын пункттер |
| **Шектеу** | қандай ереже бұзылмауы керек | орын саны, медицина, жол бар ма |

Отбасы бөлінбейді: бір отбасы — бір айнымалы, сондықтан олар бір пунктке түседі.

### Қадамдап мысал

Кішкентай есеп: 3 отбасы, 2 пункт.

| Отбасы | Адам | Медицина керек пе |
|---|---|---|
| А | 3 | иә |
| Б | 4 | жоқ |
| В | 2 | жоқ |

| Пункт | Орын | Медицина бар ма |
|---|---|---|
| П1 | 5 | иә |
| П2 | 4 | жоқ |

**Бастапқы домендер:** А тек {П1} (медицина керек), Б {П1, П2}, В {П1, П2}.

**MRV-сыз, жай ретпен (Б, В, А):**
1. Б → П1 (П1-де 1 орын қалды).
2. В → П1? 2 адам, 1 орын, сыймайды. В → П2 (П2-де 2 орын қалды).
3. А → П1? 3 адам, 1 орын, сыймайды. А-ға басқа пункт жоқ. **Тұйық!**
4. Артқа қайтамыз. В-ға басқа нұсқа жоқ, тағы артқа қайтамыз.
5. Б → П2 (П2 толды). В → П1 (3 орын қалды). А → П1 (толды). **Шешім табылды**, бірақ екі рет артқа қайттық.

**MRV-мен** (Minimum Remaining Values: «таңдауы ең аз адамды бірінші орналастыр»):
1. А-ның таңдауы біреу ғана, сондықтан А бірінші: А → П1 (2 орын қалды).
2. **Forward checking** (алдын ала тексеру): Б-ға 4 орын керек, П1-де 2 ғана. П1-ді Б-ның доменінен алып тастаймыз: Б {П2}.
3. Енді Б-ның таңдауы біреу: Б → П2 (толды). В-ның доменінен П2 кетеді: В {П1}.
4. В → П1. **Шешім табылды, бірде-бір рет артқа қайтпадық.**

MRV мен forward checking-тің пайдасы осы: тұйықты ертерек көріп, артық жұмыс істемейміз.

### Біздің картада

Ең қызығы көпір жабылғанда болады. Өзеннің батыс жағындағы 7 отбасы (21 адам) тек Мәдениет үйіне (22 орын) бара алады. Шешім бар, бірақ бір ғана орын артық қалады. Тағы 2 адамдық бір отбасы қосылса, шешім болмайды. Сонда жүйе «орын жетпейді: 23 адам, 22 орын» деп ашық айтуы керек. Адамдарды өзі бөлмейді, шешімді штаб қабылдайды.

**«Тығыз» сценарий: MRV неге керек.** Қалыпты картада 34 адамға 40 орын бар, сондықтан CSP бірден шешім табады: MRV-мен де, онсыз да кері қайту саны 0. MRV-дің пайдасын көрсету үшін [`data/scenario-tight.json`](../data/scenario-tight.json) сценарийі бар: Мәдениет үйінің бір бөлігін су басты, онда тек 8 орын қалды, мектеп 16 орынға дейін қабылдайды, емханада 10 орын. Барлығы 34 орын, яғни адам санына дәл тең. `node benchmark.js` нәтижесі:

| Әдіс | Кері қайту | Тексерілген нұсқа |
|---|---|---|
| MRV + Forward Checking | 9 | 20 |
| тек MRV | 9 | 20 |
| тек Forward Checking | 118 | 129 |
| екеуі де жоқ | 175 | 186 |

MRV кері қайтуды шамамен 19 есе азайтады. «Тек MRV» мен «MRV + FC» нәтижесі бірдей, себебі біздің кодта MRV әр отбасының **қазіргі** бос орынға сыятын пункттерін санайды: домені бос отбасы бірден таңдалып, тұйық сол сәтте табылады. Яғни бұл есепте MRV Forward Checking жасайтын жұмысты өзі де істеп қояды. Қорғауда сұрауы мүмкін.

Функцияның нақты кірісі мен шығысы: [`SPEC.md`, 5-бөлім](SPEC.md#5-csp-модулі-3-апта).

### Қорғаудағы сұрақтар

**Айнымалы, домен, шектеу деген не?**
Айнымалы — отбасы, домен — ол бара алатын пункттер, шектеулер — орын саны, медицина және жолдың болуы.

**Backtracking деген не?**
Біз бір-бірлеп таңдаймыз. Тұйыққа тірелсек, соңғы таңдауды өзгертіп, басқа нұсқаны көреміз.

**MRV не үшін керек?**
Таңдауы ең аз отбасын бірінші орналастырамыз. Ол кейінге қалса, оған орын қалмауы мүмкін. Нәтижесінде артқа аз қайтамыз.

**Forward checking не істейді?**
Әр таңдаудан кейін қалғандардың доменінен сыймайтын пункттерді бірден алып тастайды. Біреудің домені бос қалса, тұйықты бірден көреміз.

**Шешім болмаса не болады?**
Жүйе себебін жазады, мысалы «орын жетпейді», және адамдарды ережені бұзып бөлмейді.

## 3. Байес ережесі: хабарламаға қаншалықты сенеміз

### Бір сөйлеммен

Байес ережесі жаңа ақпарат келгенде бұрынғы сенімімізді қалай өзгерту керегін айтады.

### Өмірдегі мысал

Досың «ертең сабақ жоқ» деп жазды. Сен бірден сенбейсің: ол бұрын да қателескен. Бірақ екінші, үшінші адам да солай жазса, сенімің артады. Ал біреу «жоқ, сабақ бар» десе, қайтадан күмәндана бастайсың. Байес ережесі осыны сандармен есептейді.

### Үш ұғым

| Ұғым | Мағынасы | Біздің есепте |
|---|---|---|
| **Prior** (алғашқы ықтималдық) | хабар келгенге дейінгі сенім | көпірді су басу ықтималдығы 0.6 |
| **Likelihood** (шындыққа ұқсастық) | хабарлаушы қаншалықты дұрыс айтады | сенімділік r = 0.8: 10 хабардың 8-і дұрыс |
| **Posterior** (жаңа ықтималдық) | хабардан кейінгі сенім | төмендегі формуламен есептейміз |

### Формула

«Су басты» деген хабар келсе:

```
                     r · P
жаңа P = ───────────────────────────
           r · P + (1 − r) · (1 − P)
```

«Құрғақ» деген хабар келсе, `r` мен `1 − r` орындарын ауыстырамыз.

### Қадамдап мысал: көпір

Басында P = 0.6, сенімділік r = 0.8.

| Хабар | Есеп | P бұрын | P кейін |
|---|---|---|---|
| 1. «Су басты» | 0.8·0.6 / (0.8·0.6 + 0.2·0.4) = 0.48 / 0.56 | 0.600 | **0.857** |
| 2. «Су басты» | дәл солай | 0.857 | **0.960** |
| 3. «Құрғақ» | r мен 1 − r ауыстырылады | 0.960 | **0.857** |

Бір хабардан кейін-ақ P = 0.857 > 0.7, сондықтан A\* көпірді жабық деп санайды.

Көңіл аударыңыз:
- **Бір хабарға толық сенбейміз.** P бірден 1 болмайды, себебі адам қателесуі мүмкін.
- **Қарама-қайшы екі хабар бірін-бірі жояды.** 2-хабардан кейін 0.960, 3-хабардан кейін қайтадан 0.857: бір «су басты» және бір «құрғақ» хабар бір-бірін теңестірді.
- **Алғашқы ықтималдық маңызды.** Сол бір хабар қарапайым жолда (P = 0.05) ықтималдықты тек **0.174**-ке көтереді, ал суға жақын жолда (P = 0.3) **0.632**-ге. Жол өзенге жақын болса, хабарға тезірек сенеміз.
- **r = 0.5 болса**, хабар ештеңені өзгертпейді: тиын лақтырғанмен бірдей, одан ақпарат жоқ.

Функциялардың нақты кірісі мен шығысы: [`SPEC.md`, 3-бөлім](SPEC.md#3-байес-модулі-6-апта).

### Қорғаудағы сұрақтар

**Prior, likelihood, posterior деген не?**
Prior — хабарға дейінгі сенім, likelihood — хабардың шындыққа сәйкес келу ықтималдығы, posterior — хабардан кейінгі жаңа сенім.

**Неге бір хабарға толық сенбейсіңдер?**
Адамдар қателеседі немесе жағдай өзгереді. Сондықтан сенімді біртіндеп өзгертеміз. Бір хабардан кейін көпір үшін P = 0.857 болады, 1 емес.

**r = 0.5 болса не болады?**
Хабар P-ні өзгертпейді. Сенімділігі 50% хабар кездейсоқ болжамнан артық емес.

**Нәтиже қалай қолданылады?**
P жолдың бағасына қосылады, ал 0.7-ден асса, A\* ол жолмен жүрмейді.

**Шектеуі қандай?**
Барлық хабарлаушы бірдей сенімді деп алдық және су деңгейі уақыт бойынша өзгермейді деп есептедік. Уақытты ескеру үшін келесі қадам — 7-аптадағы HMM.

## Үшеуі бірге қалай жұмыс істейді

Қорғаудағы демоны осы ретпен көрсетуге болады:

1. **Байес.** Көпірге «су басты» деген хабар береміз. P: 0.6 → 0.857, көпір қызыл болады.
2. **A\*.** Көпір жабылды. Енді өзеннің батыс жағындағы үйлерден шығыс жақтағы пункттерге жол жоқ, A\* тек Мәдениет үйіне жол табады.
3. **CSP.** «Барлығын бөлу» басылады. Батыс жағындағы 7 отбасы (21 адам) Мәдениет үйіне (22 орын) түседі, шығыстағы 4 отбасы №1 мектеп пен емханаға бөлінеді. Медицина керек отбасылардың бәрі медициналық пункттерге түседі.

Бір хабар → жол өзгереді → бөлу өзгереді. Бұл — үш тақырыптың бір жүйеде жұмыс істейтінін көрсететін ең жақсы мысал.
